# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## O que é este projeto

Site + sistema de pedidos da **D'Luh Festas** (doces e salgados para festas). Não é um projeto com build/bundler/framework — são páginas HTML estáticas (com JS inline) hospedadas via Git (deploy = `git push`), mais um Cloudflare Worker que funciona como backend único, falando com Coda (banco de dados), Telegram, InfinitePay (pagamentos) e Google Calendar.

Não há testes automatizados, linter, nem etapa de build neste repositório.

## Comandos

**Site (arquivos .html na raiz):** não tem build. Editar o arquivo e o deploy é:
```
git add <arquivo.html>
git commit -m "..."
git push
```
Isso é tudo — não existe servidor de build, é puro HTML/CSS/JS estático.

**Worker (`worker-completo-pronto.js`):** este arquivo é gitignored (contém API keys hardcoded — Coda, Telegram, Google OAuth) e **nunca deve ser commitado**. Deploy é manual, direto do terminal do usuário:
```
npx wrangler deploy worker-completo-pronto.js --name coda-proxy --compatibility-date 2024-01-01
```
Qualquer mudança no worker só entra em produção depois desse comando ser executado (Claude não tem como rodá-lo — pede pro usuário rodar).

**`server.js`** (Express + `package.json`, `npm start`): proxy de TTS via Google Translate. Não está referenciado em nenhum dos arquivos HTML atuais (`painel-pedidos.html` usa a Web Speech API nativa do navegador para voz). Parece código morto/legado — confirmar com o usuário antes de assumir que está em uso.

## Arquitetura

### As 5 páginas e pra que cada uma serve

- **`index.html`** — landing page institucional. Carrega um "ticker" de produtos via `GET {WORKER}/produtos`. Link para `cardapio.html`.

**Chat Tawk.to:** `index.html`, `cardapio.html` e `empresas.html` carregam o widget de chat ao vivo do Tawk.to (script antes de `</body>`, mesma property em todas as três). `admin.html` e `painel-pedidos.html` não têm o widget — são ferramentas internas, não páginas de cliente. Conversas e configuração (cor, posição, horário) ficam no dashboard do Tawk.to, não no código. Em `cardapio.html` e `empresas.html` (as duas páginas com botão "Meu Carrinho"), há um `Tawk_API.customStyle={visibility:{mobile:{...}}}` declarado **antes** do script de embed pra subir o widget no mobile e evitar que ele fique em cima do botão do carrinho — se o offset (`yOffset:90`) precisar de ajuste fino, é só mudar esse valor (precisa continuar antes do embed pra ter efeito). A bolha própria do Tawk fica **escondida** (`Tawk_API.onLoad`/`onChatMinimized` chamam `hideWidget()`) — o único botão de chat visível na tela é o bot de status (📦); o Tawk só aparece quando acionado de dentro do bot (ver próximo parágrafo), unificando os dois chats num único ponto de entrada visual.

**Bot de triagem D'Luh (chat próprio, separado do Tawk):** em `cardapio.html` e `empresas.html`, o painel de chat próprio (FAB 📦 fixo no canto **inferior direito** — `bottom:90px`/`right:16px` no desktop, ocupando o mesmo "slot" onde a bolha do Tawk normalmente ficaria, já que ela fica escondida por padrão; no breakpoint mobile `max-width:480px` os valores encolhem proporcionalmente, ver `.status-bot-fab`/`.status-bot-panel` no CSS) deixou de ser só uma consulta de status e virou um bot de triagem completo, **orientado a botões** (`.sb-botoes`/`.sb-btn-opcao`) em vez de texto livre — o campo de texto (`#status-bot-input-row`, escondido por padrão via classe `sb-hide`) só aparece nos dois pontos que realmente precisam de digitação: telefone (status do pedido) e data (prazos/disponibilidade), controlados pela variável de estado `_sbEtapa` (`'telefone'`|`'data'`|`null`) e despachados por `sbInputSubmit()`. Quando `sbAtendente()` abre o Tawk (`showWidget()`+`maximize()`), o FAB do bot ganha a classe `.sb-lado`, que o desliza pro lado (`translateX`) em vez de ficar embaixo do widget do Tawk que acabou de aparecer no mesmo canto — a classe é removida em `Tawk_API.onChatMinimized`, voltando o FAB pra posição normal.

Fluxo (espelha `sbMenuPrincipal()` em diante no HTML): o menu principal oferece 4 opções — `sbStatusPedirTelefone()` (status do pedido), `sbNovoPedido()` (novo pedido — física fica na própria página; em `cardapio.html` esse fluxo é só "você já está no lugar certo" e **não cita nem linka o site de empresas** em nenhum ponto, em `empresas.html` ainda oferece o link de volta pro cardápio normal), `sbDuvidas()` (submenu: sabores/recheios, preços, prazos/datas, outra) e `sbAtendente()` (atendente humano). Toda folha do fluxo termina oferecendo "🔁 Voltar ao menu" e "💬 Falar com atendente" (helper `sbFimOpcoes()`), e qualquer falha de integração (Coda, Tawk, status) cai num fallback de WhatsApp com botão clicável (`sbWhatsappFallback()` — usa um botão em vez de `window.open()` direto porque o disparo normalmente vem depois de um `await` malsucedido, e nesse ponto não é mais um gesto síncrono do usuário, então o navegador pode bloquear um popup automático). Se o telefone do pedido já é conhecido (pedido recente ou salvo no `localStorage`), o bot confirma em vez de pedir de novo (`sbStatusPedirTelefone()`). Depois de 3 minutos sem interação, o bot pergunta "Ainda por aí?" e volta ao menu (`sbResetInatividade()`). Não há telemetria de intenção pro Telegram (removida de propósito — ficaria confuso misturado com as notificações que já existem lá de pedido/pagamento).

**Login obrigatório (Google/Firebase) dentro do bot:** as opções "📦 Status do meu pedido" e "❓ Tirar uma dúvida" passam primeiro por `sbExigeLogin(continuarCom)`, que checa `window._fbUser` (mesmo Firebase Auth já usado no checkout) — se já logado, segue direto pro fluxo escolhido; se não, mostra uma mensagem no próprio chat com os botões "🔵 Entrar com Google" (chama `sbFazerLogin()` → `window._fbSignIn()`, já existente) e "🔙 Voltar ao menu", e retoma automaticamente a opção escolhida assim que o login conclui. Se o login falhar/for cancelado, oferece tentar de novo, falar com atendente, ou voltar ao menu. "🛒 Fazer um pedido" e "💬 Falar com atendente" continuam sem exigir login. O fluxo pós-pedido (próximo parágrafo) não precisa de uma chamada explícita a `sbExigeLogin` porque `goCheckout()` já exige login antes de chegar no checkout — ou seja, ao confirmar o pedido o cliente já está necessariamente logado.

Status do pedido consulta **ao vivo** no Coda via `GET {WORKER}/status-pedido?tel=...` (rota só leitura). A rota busca pelos últimos 8 dígitos do telefone (mesmo critério de normalização do `/entrega-confirmada`) e retorna até 3 pedidos mais recentes daquele número, com status, itens, total, valor pago, restante, e (desde o acompanhamento pós-pedido automático) também `entrada` e `linkPagamento` (colunas "Entrada" e "Link de Pagamento" do Coda, cruas, sem cálculo); mensagens de status são traduzidas pro cliente via o mapa `STATUS_BOT_EXPLICACAO` no HTML (precisa ter uma entrada pra cada valor de `STATUS_OPTS`, senão mostra só o status crú sem explicação). Dúvidas de sabores/preços leem do cache `allProducts`/`recheios` já carregado pelo `loadProducts()` da página (sem nova chamada de rede no caso comum); só faz fetch direto a `/produtos`/`/recheios` se o cache ainda estiver vazio (`sbProdutosCache()`/`sbRecheiosCache()` — em `empresas.html` essas funções já aplicam o mesmo fallback `valorEmpresa`/`qtdMinEmpresa`/`Mostrar Empresa` que `loadProducts()` usa, pra não mostrar preço de pessoa física no bot do site B2B). Dúvida de prazos pede uma data (dd/mm/aaaa) e consulta `GET {WORKER}/horarios-disponiveis?data=...` pra dizer se ainda há horário livre naquele dia.

**Acompanhamento automático pós-pedido (seção 2.5 do spec):** ao confirmar o pedido, `abrirStatusBotPosPedido(p)` substitui o antigo `irParaWhatsapp(p.waUrl)` dentro de `_confirmarESeguirWhats()` — o painel abre em **tela cheia** (`abrirStatusBot(null, true, true)`; o 3º parâmetro `semAutoPopular` faz o painel não auto-popular menu/mensagem padrão, já que esta função monta o conteúdo sozinha), posta o **resumo do pedido como mensagem do cliente** (`p.msg`, o mesmo texto que ia pro WhatsApp — guardado em `_pedidoPendente.msg` desde o envio; os `*asteriscos*` de negrito do WhatsApp são removidos porque `sbAddMsg` usa `textContent`, que não renderiza markdown), e em seguida `sbIniciarAcompanhamento(tel,waUrl,paiId)` dispara uma checagem imediata e depois começa um **polling em `/status-pedido?tel=` a cada 12s** (`sbChecarStatusPedido()`) que roda em segundo plano até dar baixa — mesmo que o cliente feche o painel, as mensagens novas continuam sendo adicionadas e aparecem quando ele reabrir. Ao detectar `Confirmado — Esperando pagamento` **com** `linkPagamento` já preenchido (se o link ainda não tiver sido gerado pelo worker, o polling simplesmente espera o próximo ciclo), posta automaticamente o valor (`entrada`) e um botão "💳 Pagar agora" que abre o link; ao detectar `Pago — Em produção`, posta a mensagem final de agradecimento e **para o polling** (`sbPararAcompanhamento()`) — esse é o fim do que essa seção cobre (não acompanha Entregue/Finalizado). Se a consulta falhar 5 vezes seguidas (a 1ª já imediata, as demais a cada 12s — então até ~50s de tolerância a instabilidade transiente antes de desistir), o polling para e cai no fallback de WhatsApp (`sbWhatsappFallback(motivo,waUrl)` — `waUrl` é o link `wa.me` com o resumo do pedido já preenchido, o mesmo `p.waUrl` que existia antes do bot, em vez de abrir um chat em branco).
**Rastreio pelo ID do pedido, não "o mais recente da lista" (bug corrigido):** `/status-pedido` devolve até 3 pedidos por telefone, ordenados por mais recente primeiro — mas logo após criar um pedido, o Coda pode levar um instante pra refletir a linha nova nessa listagem (consistência eventual). Se o polling simplesmente pegasse `pedidos[0]`, nesse intervalo o "mais recente disponível" podia ser por coincidência um pedido **antigo** do mesmo telefone (até `Cancelado`), e o bot avisava a situação errada pro cliente que tinha acabado de fazer um pedido novo — foi exatamente isso que aconteceu num teste. Correção: `_confirmarESeguirWhats()` agora guarda `p.paiId=d.paiId` (o ID/`paiId` que `/novo-pedido` devolve na criação, que é o próprio ID de linha do Coda — o mesmo valor que aparece em `idPedido` na resposta de `/status-pedido` quando a coluna "ID Pedido" está vazia) e repassa pra `sbIniciarAcompanhamento(tel,waUrl,paiId)` → `_sbPollPaiId`. `sbChecarStatusPedido()` então busca por `pedidos.find(pd=>pd.idPedido===_sbPollPaiId)` em vez de `pedidos[0]`; se ainda não achar (linha nova ainda não apareceu), simplesmente espera o próximo ciclo (não conta como falha). Por segurança, se depois de 8 tentativas seguidas (`_sbPollNaoAchou`) o ID nunca aparecer (não deveria acontecer), desiste de rastrear por ID e volta pro critério antigo (`pedidos[0]`), pra não ficar travado em silêncio pro resto da sessão. Quando o bot é reaberto manualmente (sem vir de um pedido, `paiId` não informado), continua usando `pedidos[0]` direto, como antes. Quando reaberto manualmente pelo FAB sem ter vindo de um pedido (`abrirStatusBot()` sem argumentos), mostra o menu principal completo, como antes. Um botão "Falar com atendente" (sempre visível no rodapé do painel, além de aparecer dentro do próprio fluxo) chama `Tawk_API.showWidget()` + `Tawk_API.maximize()` pra abrir o chat humano do Tawk — como a bolha do Tawk fica escondida por padrão (ver parágrafo anterior), esse é o único jeito de chegar no atendimento humano. O fluxo de erro (`_skipParaWhatsapp()`, usado quando o registro no Coda falha) continua indo direto pro WhatsApp sem mudança — nesse caso não existe pedido salvo no Coda pro bot consultar. Como sempre, `cardapio.html` e `empresas.html` não compartilham código — o painel/CSS/JS do bot foi duplicado manualmente nos dois arquivos, com as únicas diferenças sendo o destino do link física↔empresa em `sbNovoPedidoFisica()`/`sbNovoPedidoEmpresa()` e o fallback `valorEmpresa`/`Mostrar Empresa` em `sbNormalizaProdutoBot()` (só em `empresas.html`).

**Botão de envio do pedido (`.btn-wpp`):** apesar do nome da classe (legado), o botão final de "Enviar Pedido" não menciona mais WhatsApp — nem no texto nem no ícone (ícone trocado do logo do WhatsApp pra um ícone de "enviar"/paper-plane genérico, cor trocada de `#25D366` pra `var(--accent)`). Isso porque o fluxo pós-pedido não vai mais pro WhatsApp por padrão (abre o bot de status, ver acima); a classe `.btn-wpp` continua com esse nome só por compatibilidade com o seletor `document.querySelector('.btn-wpp')` usado no JS de envio — não tem efeito visual, é só identificação interna.

**Painel "Meus Pedidos" (`cardapio.html`/`empresas.html`):** botão no header (`#mp-trigger-btn`, dentro do wrapper `.header-actions` que também contém o `auth-btn` — o `margin-left:auto` que antes ficava no próprio `auth-btn` foi movido pro wrapper, pra manter os dois colados e empurrados pro canto direito) que abre um modal (`#mp-modal-pedidos`, mesmo esqueleto `.modal-overlay`/`.modal` reaproveitado de `#mp-modal-cancelar`) com a visão completa dos pedidos do cliente — antes essa visão ficava fixa numa seção da home (`#mp-section`), removida nessa mudança. O botão aparece (sem precisar de login ainda) sempre que já existe telefone salvo no `localStorage` (`sbTelSalvo()`); ao clicar, `mpAbrirModal()` mostra um aviso com botão "Entrar com Google" (`mpFazerLogin()`) se o cliente ainda não logou, ou a lista de pedidos (chamando `mpCarregar()` na hora, pra não esperar o próximo ciclo do polling) se já logado. `mpFecharModal()` fecha. Uma vez logado, `mpInit()` (re-disparado no `DOMContentLoaded` e na atribuição final de `window._onAuthChange` — ver nota de código no handler sobre por que existe mais de uma atribuição a essa variável) também arma um polling próprio a cada 45s direto em `mpCarregar()` (`GET /status-pedido?tel=...`, mesma rota do bot), independente do polling do bot que só roda durante o acompanhamento pós-pedido — isso mantém o badge do header atualizado mesmo com o modal fechado. Dentro do modal, cada pedido aparece como um card com badge de status colorido (`MP_STATUS_CLS`), botão "💳 Pagar" quando há `linkPagamento` pendente (entrada ou restante, reaproveitando o mesmo link que o worker já gera) e botão "❌ Cancelar" quando o status ainda permite (`MP_PODE_CANCELAR`: Aguardando confirmação / Confirmado — Esperando pagamento / Pago — Em produção). Mudança de status é avisada de duas formas: um toast (`showToast`, dispara uma única vez por transição, via a marca `dluh_mp_toast_<idPedido>` no `localStorage`) e um selo "🔔 Atualizado" persistente no card até o cliente clicar nele (marca separada `dluh_mp_status_<idPedido>`, atualizada em `mpMarcarVisto()`). Além do modal, `mpRenderTriggerBadge()` (chamada a cada `mpCarregar()`) mostra ao lado do botão um badge (`#mp-trigger-badge`, reaproveitando a classe genérica `.mp-badge`+`MP_STATUS_CLS`) com o status do primeiro pedido que ainda não chegou a `Finalizado`/`Cancelado` (lista já vem do worker ordenada do mais recente pro mais antigo) — rótulo abreviado via `MP_TRIGGER_BADGE_LABEL` pra caber no espaço do header; se não houver nenhum pedido em andamento, o badge fica escondido.

**Cancelamento pelo cliente:** o botão "❌ Cancelar" do painel acima abre um modal (`#mp-modal-cancelar`, mesmo esqueleto CSS dos outros modais do site) com fluxo em duas etapas contra `POST {WORKER}/cancelar-pedido`: primeiro uma chamada de prévia (`confirmar:false`) que só calcula e mostra a taxa/reembolso sem alterar nada; ao confirmar, uma segunda chamada (`confirmar:true`) efetiva o cancelamento. Ver a seção "Cancelamento e taxa escalonada" abaixo pra regra completa da taxa.

### `worker-completo-pronto.js` — o backend

Um único Cloudflare Worker que centraliza tudo. Arquivo gitignored — **as credenciais abaixo existem só no arquivo local do usuário, nunca repita os valores reais em commits, documentação ou em qualquer lugar que vá pro Git**: API key do Coda, token do bot do Telegram, OAuth client/secret/refresh token do Google.

IDs de tabela do Coda usados pelo worker (mesmo doc, `DOC_ID`):
- `TABLE_PRODUTOS`, `TABLE_PEDIDOS`, `TABLE_ORCAMENTOS` (a principal — pedidos/orçamentos), `TABLE_RECHEIOS`, `TABLE_LIMITES`.

Principais rotas (todas roteadas por `path === '/...'` dentro de um único `fetch` handler):
`/produtos`, `/recheios`, `/horarios-disponiveis`, `/orcamentos`, `/novo-pedido`, `/webhook-telegram`, `/confirmar-estoque`, `/cobrar-restante`, `/gerar-cobranca`, `/entrega-confirmada`, `/webhook-pagamento`, `/criar-pedido`, `/pedidos-pendentes`, `/atualizar-status`, `/apagar-pedido`, `/upload-topper-imagem`, `/status-pedido` (cada pedido no retorno inclui também `entrada` e `linkPagamento`, lidos crus das colunas "Entrada"/"Link de Pagamento" — usados pelo acompanhamento automático pós-pedido do bot e pelo painel "Meus Pedidos"), `/cancelar-pedido` (`POST`, cliente cancela o próprio pedido pelo site — ver "Cancelamento e taxa escalonada" abaixo).

Integrações disparadas pelo worker: notificação no Telegram (com botão "Confirmar Estoque"), link de cobrança InfinitePay, mensagem de WhatsApp (deep link `wa.me`), criação de evento no Google Calendar.

### Ciclo de vida do Status (coluna "Status" da tabela Orçamentos no Coda)

Single-select. Os **6 valores realmente em uso hoje**, em ordem (ver `STATUS_OPTS`/`STATUS_CLS` em `admin.html`):
1. `Aguardando confirmação` (padrão/inicial)
2. `Confirmado — Esperando pagamento` (worker grava ao confirmar estoque, via Telegram ou botão no admin)
3. `Pago — Em produção` (worker grava quando o webhook do InfinitePay confirma a entrada)
4. `Entregue — Esperando restante` (worker grava via `/entrega-confirmada`, chamado pelo `painel-pedidos.html`)
5. `Finalizado` (worker grava ao confirmar pagamento do restante, ou manualmente pelo botão "Finalizar" no admin — uma vez `Finalizado`, nunca mais é sobrescrito automaticamente)
6. `Cancelado` (worker grava via `POST /cancelar-pedido`, quando o próprio cliente cancela pelo painel "Meus Pedidos" — ver seção abaixo). **Não é mais um estado terminal só pra "apagar depois"**: a decisão do negócio foi parar de apagar pedido cancelado do Coda — a row fica, com o histórico (taxa, valor retido, reembolso) anotado na coluna "Observações". `Cancelado` é tratado como status final pra fins de bloqueio (`BLOQUEADOS` no worker e `MP_PODE_CANCELAR` no front: uma vez `Cancelado`, não pode cancelar de novo) e é excluído do `STATUS_FINAL` usado por `/pedidos-pendentes` (não aparece na aba "Estoque pendente" do admin, só nas abas de Status).

Existe uma segunda coluna, **"Pedido Status"** (multi-select, controle de cozinha — ex. "Em Produção", "Entregue"), que é só informativa e serve de gatilho para auto-atualizar o Status principal (`PEDIDO_STATUS_MAP` em `admin.html`). Por ser multi-select, a API do Coda retorna essa coluna como **array**, não string — sempre tratar com `Array.isArray(...)` antes de comparar.

As Options da coluna "Status" no Coda devem corresponder exatamente às strings literais que o worker escreve — se o admin adiciona/remove um valor de `STATUS_OPTS`, o Coda precisa ter exatamente essa Option cadastrada, senão a escrita falha silenciosamente. **Isso inclui `Cancelado`** — antes de usar o cancelamento em produção, é preciso adicionar manualmente a Option `Cancelado` na coluna "Status" do Coda (mesma observação vale pro botão "Finalizar"/outros valores já existentes).

### Cancelamento e taxa escalonada

Regra de negócio (decidida com a D'Luh): o cliente pode cancelar o próprio pedido em qualquer fase anterior à entrega, mas perto da data da entrega passa a haver uma taxa de cancelamento, porque ingredientes já foram comprados e a produção pode já ter começado.

- **Carência de 2 dias:** contados a partir de quando o pedido foi criado (`row.createdAt` do Coda — não existe uma coluna dedicada de "data da confirmação", então `createdAt` é usado como proxy). Dentro desse prazo, cancelamento é **sem taxa**, reembolso integral do que já foi pago.
- **Depois da carência:** a taxa cresce **linearmente** de 0% até um teto de **80%**, entre o fim da carência e a data de entrega (`Data Desejada`). Ou seja, quanto mais perto da entrega, maior a taxa — no dia da entrega (ou depois), a taxa é o teto de 80%.
- **Pedido de última hora** (prazo total entre pedido e entrega ≤ 2 dias, ou seja, nunca chega a existir uma janela de carência real): qualquer cancelamento depois do pedido feito já cai direto no teto de 80%.
- **Sem pagamento, sem taxa:** se `Valor Pago` ainda é zero (cliente nunca pagou a entrada), a taxa é sempre 0% — não tem o que reter.
- A taxa incide sobre o **valor efetivamente pago** (`Valor Pago`), não sobre o valor da entrada-alvo nem sobre o total do pedido.
- Implementado em `calcularTaxaCancelamento(dataPedido, dataEntrega, agora, valorPago)` no worker; usado por `POST /cancelar-pedido`, que segue um fluxo de duas chamadas — prévia (`confirmar:false`, só calcula e devolve `feePct`/`valorRetido`/`valorReembolso`, sem alterar nada) e confirmação (`confirmar:true`, grava `Status='Cancelado'` + nota em "Observações", e dispara Telegram). Bloqueia cancelamento se o pedido já está `Cancelado`, `Entregue — Esperando restante` ou `Finalizado`. Mesma checagem de segurança do `/status-pedido` (últimos 8 dígitos do telefone precisam bater com a coluna "WhatsApp" do pedido).
- Notificação ao Telegram é marcada como **urgente** (🚨, em vez do ❌ padrão) sempre que `feePct > 0` — ou seja, sempre que o cancelamento já está fora da carência e implica reter algum valor, pra equipe tratar com prioridade (reembolso parcial, possível necessidade de já ter comprado insumos, etc.).
- **80% foi o valor que a D'Luh propôs; está implementado como teto fixo (`TETO` em `calcularTaxaCancelamento`).** Pra mudar, é só esse número no worker — não precisa tocar no front (cardapio.html/empresas.html só exibem o `feePct` que a rota devolve).
- **Existe um segundo caminho de cancelamento, separado deste: o botão "🗑️ Apagar" do admin.** Esse caminho não passa por `/cancelar-pedido` nem pela taxa escalonada acima — `/apagar-pedido` (worker) só dispara o botão-coluna "DEL" da tabela Orçamentos no Coda, então o que de fato acontece é 100% definido pela fórmula desse botão **dentro do Coda**, fora do nosso código. Essa fórmula foi ajustada pelo usuário pra já alterar o status antes de apagar (e apagar seletivamente o que deve ser apagado) — ou seja, é um "cancelar apagando" de uso interno/admin, intencionalmente distinto do soft-cancel (`Status='Cancelado'`, mantém a linha) que o cliente usa pelo site. Ajustes futuros nessa fórmula são feitos direto no Coda, sem precisar mudar nada aqui.

### Colunas extras pro fluxo de Empresas

- Tabela **Produtos**: colunas `Valor Empresa` (preço unitário B2B) e `Quanti. Empresa` (quantidade mínima B2B), paralelas a `Valor`/`Quantidade mínima`. O worker (`/produtos`) lê as duas e expõe `valorEmpresa`/`qtdMinEmpresa` na resposta, com fallback pro valor normal quando a coluna empresa está vazia num produto — então é seguro deixar produtos sem preço B2B definido ainda.
- Tabela **Produtos**: coluna `Mostrar Empresa` (checkbox), paralela a `Mostrar`. Mesma semântica (`!== false` esconde o produto), mas só afeta o catálogo de `empresas.html` — `Mostrar` continua controlando `cardapio.html`/`index.html` normalmente, sem mudança. O worker (`/produtos`) expõe `mostrarEmpresa` na resposta; o filtro acontece client-side em `empresas.html` (`loadProducts()`), em cima do array que já passou pelo filtro de `Mostrar`. Por ser coluna nova, produtos existentes nascem **desmarcados** — ficam ocultos no site de empresas até alguém marcar manualmente os que devem aparecer lá.
- Tabela **Orçamentos**: coluna `Tipo Cliente` (single-select, precisa ter a Option `Empresa` cadastrada) — `empresas.html` grava esse valor no row pai a cada pedido; `cardapio.html` não grava nada nela (fica em branco = cliente pessoa física). O worker (`/pedidos-pendentes`) repassa esse campo como `tipoCliente`, e `admin.html` mostra um badge "🏢 Empresa" no card quando esse valor é `'Empresa'`.
- Se essas colunas não existirem no Coda com esses nomes exatos, a leitura/escrita falha silenciosamente (mesmo padrão de risco já documentado pra `STATUS_OPTS`).

- Painel "Meus Pedidos" virou botão no header + modal: a antiga seção fixa na home (`#mp-section`) foi removida; agora um botão (`#mp-trigger-btn`, ao lado do `auth-btn`, dentro do novo wrapper `.header-actions`) abre um modal (`#mp-modal-pedidos`, reaproveitando o esqueleto `.modal-overlay`/`.modal` já usado em `#mp-modal-cancelar`) com a mesma lista de pedidos/login de antes. - Bugfix no acompanhamento pós-pedido — rastreio pelo ID, não "o mais recente da lista": `sbChecarStatusPedido()` confiava em `pedidos[0]` como sendo o pedido recém-criado, mas a listagem do Coda pode demorar um instante pra refletir a linha nova (consistência eventual) — nesse intervalo, `pedidos[0]` podia ser por coincidência um pedido **antigo** do mesmo telefone (até `Cancelado`), e o bot avisava a situação errada pro cliente que tinha acabado de fazer um pedido novo. Corrigido guardando o `paiId` devolvido por `/novo-pedido` e rastreando por esse ID (`_sbPollPaiId`) em vez de posição na lista, com tolerância a "ainda não apareceu" (espera o próximo ciclo) e um fallback de segurança pro critério antigo depois de 8 tentativas sem achar. Replicado em `cardapio.html` e `empresas.html`.

## Cuidados ao editar

- **Nunca** commitar `worker-completo-pronto.js` (está no `.gitignore` por conter credenciais). Mudanças nele só viram produção quando o usuário roda o `wrangler deploy` manualmente.
- Mudanças nos `.html` da raiz só viram produção depois de `git push` — feito pelo próprio usuário (o commit/push não costuma ser feito de dentro do sandbox de forma confiável).
- Ao tocar na coluna "Pedido Status" (Coda), lembrar que ela chega como array (multi-select).
- Ao adicionar/remover um valor em `STATUS_OPTS` (`admin.html`), replicar a mudança nas Options da coluna "Status" no Coda. Isso vale pra `Cancelado`: a Option precisa existir no Coda com esse nome exato antes do cancelamento pelo site funcionar de ponta a ponta (senão a gravação do `Status='Cancelado'` falha silenciosamente).
- `painel-pedidos.html` tem um token do Coda hardcoded no cliente — risco de segurança conhecido, não introduzir mais segredos client-side do que já existe.
- `empresas.html` e `cardapio.html` não compartilham código (cada um é um arquivo HTML independente) — uma correção de bug ou feature nova num (ex.: cálculo de frete, upload de topper, painel "Meus Pedidos", cancelamento) só entra no outro se for replicada manualmente.
- `window._onAuthChange` é atribuído **duas vezes** em `cardapio.html`/`empresas.html` (um wrapper mais acima que chama `initStatusBar` — código legado de uma barra de status via Firestore, hoje sem uso real — e uma atribuição final na seção "AUTH & HISTÓRICO" que de fato fica valendo, porque sobrescreve a primeira). Qualquer novo hook em mudança de auth (como o `mpInit()` do painel "Meus Pedidos") precisa entrar na atribuição **final**, não na de cima, senão nunca executa.
